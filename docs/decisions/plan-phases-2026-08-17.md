## 1. Phase 0 — One server instrumented by hand · CLOSED 2026-08-18

**Revised from the original plan.** The first version called for instrumenting all three
remotes as soon as possible, on the grounds that history cannot be recovered retroactively.
Conscious decision not to: metrics from all three are not urgent, and it avoids doing by hand,
three times, work the generator will do on its own. The accepted cost is less history on
`madrid-prod` and `marsella-prod`; taken knowingly.

Scope cut to the minimum that allows building and testing the application:

- `node_exporter` + `cAdvisor` **on `marsella-test` only**, bound to its Tailscale IP. It is the
  test server: if something breaks, there are no clients in front of it.
- Prometheus on the home server, pointing at Tailscale **IPs** (not MagicDNS: Prometheus runs in
  a container and does not inherit the host's resolver).
- The `stack.client` label on containers, preserved by cAdvisor. cAdvisor **does not export labels
  by default**: it has to be asked with `--whitelisted_container_labels`. Forget it and everything
  appears to work while the figure answering "what does each client cost" simply is not there.
- Alertmanager with the capacity rules (`predict_linear` over disk and RAM).
- ~~Grafana as a temporary PromQL workbench.~~ Never needed: the queries were short enough to
  write directly, and Chart.js draws the charts. Dropped 2026-08-25.

`madrid-prod` and `marsella-prod` were instrumented later **using atalaya's generator**, which is
also how we found out whether the generator was worth anything. It was: the second one needed no
fixes (2026-08-19).

The installation artifact was written as a product from the start rather than as scaffolding,
because it had two lives: run by hand on `marsella-test` first, generated by atalaya later. Bash
rather than Ansible, for the reason in *The installation artifact* in
[architecture.md](../architecture.md).

## 2. Phase 1 — atalaya v1: read-only, plus registration · CLOSED 2026-08-19

Monorepo scaffolding modelled on `compas`: `backend/` (NestJS), `frontend/` (Angular),
`backend/prisma/`, orchestrated from the root with `concurrently` rather than npm workspaces.
Tailscale identity guard, initial SQLite schema.

**Inventory** module: for each registered server, one fixed command (`stack inventory`) over SSH,
cached in SQLite with periodic refresh.

Screens:

- **Overview** — one card per server: instances, how many are down, last backup.
- **Server** — its instances with deployed version, status, and **direct links to the domains**
  of each.
- **Instance** — detail: catalogue app, current and previous version, domains, health.
- **Backups** — status and date of the last full and the last incremental backup per server,
  with the failure reason where there was one. Two, because "no incremental since yesterday" and
  "no full since last month" are different failures.

**Server registration** belonged in v1 despite the "read-only" label, because it modifies no
remote server: it only generates text and makes HTTP requests. Step 4 — verifying — is what
provides something that did not exist: the hard part of provisioning is not typing the command,
it is knowing which command, with which IP, and knowing whether it worked.

## 3. Phase 2 — Metrics, incidents, notifications · CLOSED 2026-08-23

A Prometheus query service in the backend, with a catalogue of named PromQL queries (no loose
PromQL from the front end). Charts of our own in Angular: CPU/RAM/disk series per server,
per-container usage, and the projection of days until disk fills or RAM runs out.

`POST /webhooks/alertmanager` → incident inbox in the app, unifying capacity, downed services,
certificates and backups in a single place. The same webhook drives notification delivery.
Recipients and routing became an editable screen; silences are pushed to Alertmanager's REST API.
Certificate expiry was the last item, closed with `blackbox_exporter`.

## 4. Phase 2.5 — Mobile · CLOSED 2026-08-23

Inserted ahead of Phase 3: the panel was desktop-only. Two real blockers were fixed: the sidebar
became a `MobileNavService`-driven off-canvas drawer below the `lg` breakpoint, and the server
page's 8-column instance table gained a stacked-card twin. Dialog widths and grid columns were
made responsive. Verified with Playwright at 375×812.

## 5. Phase 2.6 — Monitoring the monitor · CLOSED 2026-08-25

Inserted ahead of Phase 3: `homeserver` itself was the one machine nothing watched. `Server`
gained a `kind` discriminator (`stack` | `host`) — a `host` server skips the SSH inventory
entirely and takes its health from Prometheus, which is what makes a machine without `stack`
representable at all. Its collectors are two more services in the same compose file, registered
on boot rather than through the UI.

Adding it exposed an assumption that was already wrong: the panel showed one disk per server,
hardcoded to `/`. Every mount is shown now, per-disk alert switches replace the special-casing,
and a collector permission bug that had been hiding disks on every machine got fixed on the way.

Also folded in here: **per-app volume sizes**, measured by `backup.sh` and read back through
`stack inventory`. And the install: one process, valid anywhere. Configuration collapsed to a
single `.env` beside the compose file, the runtime-directory copy dance dropped in favour of
running from a clone, and the machine-specific deploy scripts deleted. The repo was made public to
support it, after auditing the history for credentials (none) and replacing real addresses,
tailnet names and client names with placeholders.

## 6. Phase 3 — Actions · CLOSED 2026-08-27

`status`, `versions`, `logs`, `deploy`, `rollback`, `start`, `stop` and `backup` over SSH, with
live output over SSE, explicit confirmation naming what is about to change, and every mutating
run recorded in `AuditEntry` — its first writer, having sat unused since the initial migration.

The blocker was never the UI: the `atalaya` account has no docker and cannot read `.env`, so
everything past `inventory` was unreachable. Solved with a root-owned dispatcher and a single
wildcard-free sudo rule; the reasoning, the rejected alternatives and what it honestly costs are
in [stack-integration.md](../stack-integration.md).

Out of scope at the time, each for its own reason: **`exec`** is a remote shell and stays
prohibited; **`retire`** is destructive and needed a type-the-name gate before it was offered
(added 2026-08-30, in both its forms); **`add`** writes secrets and belonged with Phase 4 (added
2026-08-30, Phase 4.5).

Provisioning is **not here**: it was solved in v1 by generating the artifact instead of running
it, and there is no intention of later "promoting" it to remote execution.

## 7. Phase 4 — Environment variables · CLOSED 2026-08-30

An editor for `secrets/<instance>.env` with the schema derived from `services[].env` in
`apps.json`: which variables the app requires, which are missing, which are set. Write-only,
preserving 600 permissions. Plus the part the description did not anticipate — a saved change is
not a live change, so the panel offers the redeploy that applies it.

The contract is `stack secrets <inst> {--json|--set}`, and the value travels on **stdin**: as an
argument it would be visible in `ps` on the server. Setting is limited to variables `apps.json`
declares; unsetting is not, so leftovers can be cleared.

**Building it found a hole in Phase 3.** The atalaya account could write `stack` itself — the
program the dispatcher runs as an account in the docker group — because it is in the owner's group
and Ubuntu's default umask leaves group write on everything `git pull` writes. The allowlist was
bounding what could be asked for while the program answering could be replaced. Fixed in three
places, including a check inside the dispatcher that fails closed; see *The dispatcher could be
bypassed* in [stack-integration.md](../stack-integration.md).

## 8. Phase 4.5 — Creating an instance · CLOSED 2026-08-30

`stack add` from the panel: the last thing that needed a terminal. Not a phase of its own when
the plan was written — it became one once the declaration stopped being a git-tracked file with
two owners, which is what made creating an instance an ordinary dispatcher entry rather than a
fight with the repository.

It is the widest entry in the allowlist and the only one carrying values that are not names, so
its dispatcher case parses its arguments instead of matching a fixed shape. What it may **not**
carry matters as much as what it may — `--catalogue` and `--secrets-dir` would point `stack` at
files of the caller's choosing.

Two entries for one command, as with `secrets`: `--dry-run` writes nothing and is a `read`, so the
panel shows what the server itself worked out before anyone commits to it.

**It also fixed a real alert.** A newly declared instance was probed for its certificate before it
had one, so it alerted through the whole DNS-then-variables-then-deploy sequence. The probe list
now follows what is *deployed*, not what is declared.

## 10. Changes to the `stack` repo · CLOSED 2026-08-23

The plan named two, both small and of immediate value even if atalaya never got built. Both done;
names ended up English (`stack_backup_success`, `stack_deploy_info`…), not the Spanish ones first
drafted, per the *English throughout* revision:

- **`scripts/backup.sh`** writes a `.prom` file into node_exporter's textfile collector directory
  with a success gauge and a last-success timestamp. In exchange backup status gained a year of
  history and the "no successful backup for 26 hours" alert — which is what actually warns you
  when the cron job stopped firing.
- **`stack`** exports the deployed version per instance the same way, as a metric with a
  `version` label. Ranging over it *is* the deployment history; the instance page draws it.

`stack` grew far more than two changes in the end (`inventory`, `catalogue`, `secrets`, `add
--json`, `versions --json`, the declaration leaving git). All in
[stack-integration.md](../stack-integration.md).

## 11. Plan revisions

**2026-08-17 — Tailscale as a prerequisite, not a parallel task.** Collectors must bind to the
tailnet IP; without a tailnet there is nothing to bind them to. All four nodes joined that day.

**2026-08-18 — Provisioning stays outside atalaya.** The previous version left it as external
preparation, and turning it into remote execution from the application was considered. Discarded:
atalaya generates the artifact and verifies the result, but does not install. This removes the
need for remote `sudo` at the root, and lets server registration land in the read-only v1 instead
of waiting for Phase 3.

**2026-08-18 — Phase 0 cut to a single server.** The "instrument all three now because history
cannot be recovered" argument is dropped. `marsella-test` only; the other two via the generator,
which thereby tests itself.

**2026-08-18 — Alert delivery moves into atalaya, and channels stop being exclusive.** The
original plan had Alertmanager sending by Telegram. The split changes: Alertmanager forwards to
atalaya and atalaya notifies, because Alertmanager's configuration is file-only and the premise
is that this must be configurable from the web UI. Since delivery is then our own code, channels
coexist and are toggled from the UI rather than chosen once, routed by severity.

**2026-08-18 — No bypass route; the watchdog runs through atalaya.** A static route in
`alertmanager.yml` bypassing the application was planned, and Telegram was picked for it. Dropped
on the objection that it made an unwanted channel load-bearing. Rethinking it showed the route
was redundant: routing the watchdog heartbeat *through* atalaya means its outage already stops
the pings and healthchecks.io reports it. One path, exercised every five minutes, instead of two
where the emergency one is never tested.

**2026-08-18 — English throughout.** Repository language switched from Spanish to English, files
and CLI flags included. `stack` followed, so the label is `stack.client` and the script
`backup.sh`.

**2026-08-27 — "v1 is read-only" stops being true.** Phases 3 to 4.5 made the panel able to run
every `stack` operation that has a place in a panel. The constraint that survives is not
"read-only" but "a fixed list, through a dispatcher, with an audit row".
