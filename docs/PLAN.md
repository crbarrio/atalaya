# atalaya — server management and monitoring panel

## Context

There are three servers today (`madrid-prod`, `marsella-prod`, `marsella-test`) running the
deployment engine from the `stack` repo. All operations are done by SSH-ing into each machine
and running `./stack` by hand: there is no combined view, no way to tell at a glance which
version each instance runs, whether the last backup succeeded, or how much RAM and disk
headroom each machine has left. New clients are being onboarded onto small servers with no
measured figure for what each client costs or how many more fit.

`atalaya` is a self-hosted web application on the home server that unifies both halves of the
problem: **commanding** (running `stack` on any server, editing each app's variables, shortcuts
to the deployed domains) and **watching** (CPU, RAM, disk, per-container usage, backup status,
incidents), all within a single interface of its own — without jumping to external tools.

New repo, independent of `stack`. This plan touches `stack` in two minor places only, listed at
the end.

## Decisions made

| Decision | Choice |
|---|---|
| Server access | SSH over Tailscale. No agent on the machines. |
| Metrics | Prometheus as an **invisible** engine. The UI is our own. |
| Presentation | Angular + a charting library. No Grafana in the product. |
| Authentication | Tailscale Serve (`Tailscale-User-Login` header), with a local login fallback. |
| Order | App first. One server instrumented by hand (`marsella-test`); the rest via the generator. |
| v1 | Read-only, **plus server registration** (generates and verifies; does not execute). |
| Provisioning | atalaya **generates the artifact and verifies the result**. It never installs. |
| Control node | `homeserver`, with its own SSH key. Not a workstation. |
| Prometheus targets | File-based discovery (`file_sd_configs`), regenerated by atalaya. |
| Alert delivery | Alertmanager groups and forwards to atalaya; **atalaya sends the notification**. |
| Alert channels | Several, coexisting. Enabled and routed per severity from atalaya's UI. |
| Monitoring the monitor | Watchdog heartbeat **through atalaya** to healthchecks.io. |
| Bypass route | None. See *Why there is no bypass route*. |
| Stack | NestJS + Angular + Prisma + SQLite, laid out as in `compas`. |
| Language | English throughout, code and documentation alike. |

## Architecture

Three layers, and only one gets built:

- **Collection and storage** — `node_exporter` + `cAdvisor` on each remote server (listening
  *only* on the Tailscale IP), `Prometheus` on the home server. Long retention (≈395 days). No
  interface; nobody ever opens it.
- **Rules and alerting** — Prometheus rules + Alertmanager, configured in YAML. Alertmanager
  delivers by webhook to atalaya, which stores and displays them.
- **Presentation and control** — atalaya. The only thing being developed.

atalaya's data sources:

1. **Prometheus HTTP API** (`/api/v1/query`, `/api/v1/query_range`) for every number and chart.
   atalaya **stores no metrics**; that is what keeps it small.
2. **SSH** (`ssh2`) to read `stack`'s state and, later on, to run actions.
3. **Alertmanager webhook** for the incident inbox.

SQLite holds only: the server registry and access credentials, received incidents, the action
audit trail, and an inventory cache.

### Security — non-negotiable constraints

- The process listens on **`127.0.0.1` only**. Without this, Tailscale's identity header is
  forgeable by anyone on the tailnet.
- `tailscale serve`, never `tailscale funnel`.
- **Never a free shell over SSH.** The backend composes `stack <subcommand> <instance>` from a
  closed list of subcommands and instance names validated against `state/manifest.json`. No
  interpolating user text into a command.
- A dedicated SSH user per server, a key exclusive to atalaya, minimal `sudo`. The key lives on
  `homeserver`, not on a workstation. Since Phase 3 that `sudo` is exactly one line: the account
  may run `/usr/local/sbin/atalaya-stack` as `ubuntu`, a root-owned dispatcher holding the list
  of `stack` subcommands it accepts. No wildcard, and the list is in a file the account cannot
  write. **Nor can it write the program the dispatcher runs** — that was not true until Phase 4
  found it, and it made the allowlist decorative. Details in
  [stack-integration.md](stack-integration.md).
- **atalaya does not provision by itself.** It generates the installation artifact and checks the
  result, but a person supplies the `sudo` that installs it, once. This is not a limitation to be
  overcome later — it is what stops the panel from becoming a machine capable of installing
  software as root across the whole fleet. Running a fixed list of `stack` subcommands on an
  already-provisioned machine is a different thing, and is what the dispatcher above bounds.
- The artifact is **downloaded and read before being run**. No `curl … | sudo bash`: the
  shortcut normalises running code nobody has looked at as root, and turns any flaw in atalaya
  into direct access to all three servers.
- Secrets are **write-only**: variables can be written and rotated, an existing value is never
  displayed. What *is* shown is *which variables are missing*, derived from the schema.
- Every action with an effect is recorded in the audit table.

## Phases

### Phase 0 — One server instrumented by hand

**Revised from the original plan.** The first version called for instrumenting all three
remotes as soon as possible, on the grounds that history cannot be recovered retroactively.
Conscious decision not to: metrics from all three are not urgent, and it avoids doing by hand,
three times, work the generator will do on its own. The accepted cost is less history on
`madrid-prod` and `marsella-prod`; taken knowingly.

Scope cut to the minimum that allows building and testing the application:

- `node_exporter` + `cAdvisor` **on `marsella-test` only**, bound to its Tailscale IP. It is the
  test server: if something breaks, there are no clients in front of it.
- Prometheus on the home server, pointing at Tailscale **IPs** (not MagicDNS: Prometheus runs in
  a container and does not inherit the host's resolver).
- The `stack.client` label on containers, preserved by cAdvisor. cAdvisor **does not export labels by
  default**: it has to be asked with `--whitelisted_container_labels`. Forget it and everything
  appears to work while the figure answering "what does each client cost" simply is not there.
- Alertmanager with the capacity rules (`predict_linear` over disk and RAM). See *Alerting*
  below for how delivery is arranged.
- ~~Grafana as a temporary PromQL workbench.~~ Never needed: the queries were short enough to
  write directly, and Chart.js draws the charts. Dropped 2026-08-25.

`madrid-prod` and `marsella-prod` get instrumented later **using atalaya's generator**, which is
also how we find out whether the generator is worth anything.

### The installation artifact

A single piece, in `infra/fleet/server-setup/`, versioned in git, with two lives:

1. **Today**: run by hand on `marsella-test`.
2. **Later**: it is what atalaya generates, parameterised, from the browser.

Hence written as a product from the start rather than as scaffolding: idempotent, parameterised
by arguments (host, tailnet IP, labels), and readable in one sitting.

**Bash, not Ansible.** Not a matter of taste: Ansible pushes from a control node towards the
machines, and the chosen model is the opposite — a self-contained artifact handed to the user to
run *on* the new machine. A playbook cannot be "downloaded and run there"; a script can.

## Alerting

Two separate things that are easy to conflate: **notifying** is pushing something at you when
you are not looking; **the inbox** is a place to review what happened. atalaya provides both,
and they are not alternatives.

### Where the configuration lives

Alertmanager is configured by a YAML file and has **no API for changing its configuration**.
Since "configurable from atalaya's web UI" is a premise, that constraint decides the design.

**Alertmanager forwards everything to atalaya over a webhook, and atalaya sends the
notification.** Recipients, channels, per-severity routing and quiet hours are rows in SQLite,
edited through the UI. No file generation, no reload, and no template bug that silently kills
alerting.

### Channels are not exclusive

Because delivery is atalaya's code rather than Alertmanager routing, channels are a table —
type, credentials, enabled, which severities it takes — and adding one is writing an adapter.
Email and Telegram coexist; each is switched on and configured from the UI.

They are also complementary rather than interchangeable, by urgency. "Backup failed last night"
or "this disk fills in 4 days" are email: read calmly, with context, kept in the inbox.
"marsella-prod is not responding" is a push to the phone. That is routing by severity, and it is
exactly the sort of thing worth expressing in the panel.

Implementation note: design the adapter interface for several channels from the start, but write
**one** first. Three half-finished adapters are worse than one that works; the second takes an
afternoon once the first is proven.

The alternative — atalaya generating `alertmanager.yml` and reloading — was rejected. It makes
the UI a disguised YAML editor: the form has to map onto Alertmanager's nested routing tree with
inheritance between levels, so atalaya would inherit Alertmanager's configuration model as its
own interface model. And a bad generated file breaks alerting silently, which is discovered on
the day the alert was needed.

What Alertmanager keeps is the hard part, which we do not want to reimplement: grouping,
deduplication, inhibition (do not report ten downed services when the truth is one downed
server) and silencing.

Note that **silences do have a REST API**, unlike configuration. So "silence this for 2 hours"
from atalaya's UI is an HTTP call, not a generated file. Configuration in our database,
silences against their API, and `alertmanager.yml` stays a short file that is versioned and
rarely touched.

### Watching the watchman

Absence of alerts is ambiguous: everything may be fine, or Prometheus may have stopped three
days ago. From the inside those two states are identical, and no system reliably detects its own
death.

A `Watchdog` alert with `expr: vector(1)` is therefore permanently firing, and Alertmanager
forwards it as a steady heartbeat. **The heartbeat goes through atalaya**, which pings
**healthchecks.io** — an external service that does nothing while pings arrive and notifies when
they *stop*.

Routing it through atalaya rather than around it is the deliberate choice. The heartbeat then
crosses the entire chain — Prometheus evaluating, Alertmanager routing, atalaya's notifier, the
home network, the internet link — so a break anywhere is noticed, including the two cases nothing
else covers: a power cut at home, and atalaya itself being down.

The watchman must be external. One running on the same machine watches nothing.

### Why there is no bypass route

The obvious objection to routing everything through atalaya is that its own outage would leave us
blind. The usual answer is a static route in `alertmanager.yml` that bypasses the application.
Rejected, for two reasons.

First, it is **redundant**. The failure it covers — atalaya down, notifications not going out —
is already detected by the watchdog, precisely because the heartbeat runs through atalaya. When
atalaya dies the pings stop and healthchecks.io says so, from outside.

Second, **an emergency path that is never exercised does not work.** A bypass used once a year is
where the token has expired, the address changed, or the provider altered its API — and nobody
noticed, because nothing ever travelled that way. The watchdog path is exercised every five
minutes and is therefore continuously proven. Rather than maintaining a second, untested path, we
prove the only path there is, constantly.

The cost, stated plainly: while atalaya is down we get the fact that the system is broken, not
the content of the alerts. Two things make that acceptable. Alertmanager **retries the webhook**,
so alerts still firing are delivered once atalaya returns — a delay, not a loss; what can be
missed is something that broke and healed during the outage. And on being told the monitoring is
down, the next action is to go and look anyway, where the content is waiting.

This is also what keeps a channel we do not want from becoming load-bearing. There is one path,
one place where routing is configured, and no second system to keep alive.

### Alert fatigue

One downed server can generate dozens of notifications if grouping is left at defaults. By the
third day they stop being read and the system stops being worth anything. Grouping keys, wait
windows and repeat intervals are decided deliberately, not inherited.

### Email transport

**Not decided yet, and no longer blocking.** One constraint is settled: no self-hosted MTA on
`homeserver`. Outbound mail from a residential IP lands in spam or gets rejected — the kind of
thing that works in testing and fails on the day it matters. The domain `example.com` is
available, which makes a transactional provider with SPF and DKIM the likely answer.

The dead man's switch does not wait for this decision: healthchecks.io notifies through its own
channels. So the "everything is broken" case is covered before any SMTP question is settled.
What does wait is ordinary alert delivery, which has nowhere to go until a channel exists.

### Phase 1 — atalaya v1: read-only

Monorepo scaffolding modelled on `compas`: `backend/` (NestJS), `frontend/` (Angular),
`backend/prisma/`, orchestrated from the root with `concurrently` rather than npm workspaces.
Tailscale identity guard, initial SQLite schema. Layout details and divergences in
[app.md](app.md).

**Inventory** module: for each registered server, read `state/manifest.json`,
`state/<inst>.version`, `state/<inst>.previous` and `backups/last_status` over SSH; combine
with `apps.json` and `servers/<server>.json`. Cache in SQLite with periodic refresh.

Screens:

- **Overview** — one card per server: instances, how many are down, last backup.
- **Server** — its instances with deployed version, status, and **direct links to the domains**
  of each (`domains[]` from `servers/<server>.json`).
- **Instance** — detail: catalogue app, current and previous version, domains, health.
- **Backups** — status and date of the last full and incremental backup per server, with the
  failure reason where there was one.

**Server registration** module. It belongs in v1 despite the "read-only" label, because it
modifies no remote server: it only generates text and makes HTTP requests.

1. The server is registered (name, host, tailnet IP) in SQLite.
2. atalaya **generates the artifact already personalised** — that IP inside it, its labels, its
   ports — to download or copy.
3. A person runs it on the new machine.
4. atalaya **verifies**: does `node_exporter` answer on `100.x:9100`? Does cAdvisor? Does
   Prometheus see the target as `UP`? A traffic light per check until everything is green.

Step 4 is what provides something that does not exist today. The hard part of provisioning is
not typing the command: it is knowing which command, with which IP, and knowing whether it
worked. atalaya can know all three without touching the machine.

To close registration without editing files by hand, **Prometheus reads its targets through
file-based discovery** (`file_sd_configs`) from a JSON file atalaya regenerates from its
database. Prometheus re-reads it on its own, without a restart. atalaya writes a file on its own
machine: it touches nothing remote and needs no special permissions, and registration is still
complete end to end. Same pattern `stack` already uses: the database rules, the configuration is
derived.

### Phase 2 — Metrics in the app

A Prometheus query service in the backend, with a catalogue of named PromQL queries (no loose
PromQL from the front end). Charts of our own in Angular: CPU/RAM/disk series per server,
per-container usage aggregated by the `stack.client` label, and the projection of days until disk
fills or RAM runs out.

`POST /webhooks/alertmanager` → incident inbox in the app, unifying capacity, downed services,
certificates and backups in a single place. Same webhook drives notification delivery: see
*Alerting* above. Recipients and routing become an editable screen; silences are pushed to
Alertmanager's REST API.

### Phase 2.5 — Mobile — Done, 2026-08-23

Inserted ahead of Phase 3, 2026-08-23: the panel was desktop-only. Viewport meta tag and
Tailwind v4's default breakpoints were already there to use. Two real blockers were fixed: the
sidebar is now a `MobileNavService`-driven off-canvas drawer (hamburger toggle, backdrop,
auto-close on nav) below the `lg` breakpoint, sticky/always-visible above it; and the server
page's 8-column instance table now has a parallel stacked-card layout (`md:hidden`) alongside
the desktop table (`hidden md:block`). Dialog widths (register-server, channel-form-dialog) and
grid columns were made responsive (`w-[95vw]`/`grid-cols-1 sm:grid-cols-2`), and several rows
(Danger zone, notification channels, the history chart's peak-stats header) got `flex-col`/
`flex-wrap` fixes to avoid narrow-screen overflow. Verified with Playwright at 375×812: drawer
opens/closes correctly, no horizontal page overflow on overview/servers/server-detail.

### Phase 2.6 — Monitoring the monitor — Done, 2026-08-25

Inserted ahead of Phase 3: `homeserver` itself was the one machine nothing watched. `Server`
gained a `kind` discriminator (`stack` | `host`) — a `host` server skips the SSH inventory
entirely and takes its health from Prometheus, which is what makes a machine without `stack`
representable at all. Its collectors are two more services in the same compose file, registered
on boot rather than through the UI. Details in [monitoring.md](monitoring.md).

Adding it exposed an assumption that was already wrong: the panel showed one disk per server,
hardcoded to `/`. Every mount is shown now, per-disk alert switches replace the special-casing,
and a collector permission bug that had been hiding disks on every machine got fixed on the way.

Also folded in here: **per-app volume sizes**, measured by `backup.sh` (the one place with docker
access that already walks every volume) and read back through `stack inventory`. See
[monitoring.md](monitoring.md).

And the install: one process, valid anywhere. Configuration collapsed to a single `.env` beside
the compose file, the runtime-directory copy dance dropped in favour of running from a clone, and
the machine-specific deploy scripts deleted — they were gitignored, so they were never the
install path for anyone but this workstation. The repo was made public to support it, after
auditing the history for credentials (none) and replacing real addresses, tailnet names and
client names with placeholders.

### Phase 3 — Actions — Done, 2026-08-27

`status`, `versions`, `logs`, `deploy`, `rollback`, `start`, `stop` and `backup` over SSH, with
live output over SSE, explicit confirmation naming what is about to change, and every mutating
run recorded in `AuditEntry` — its first writer, having sat unused since the initial migration.

The blocker was never the UI: the `atalaya` account has no docker and cannot read `.env`, so
everything past `inventory` was unreachable. Solved with a root-owned dispatcher and a single
wildcard-free sudo rule; the reasoning, the rejected alternatives and what it honestly costs are
in [stack-integration.md](stack-integration.md).

Out of scope, each for its own reason: **`exec`** is a remote shell and stays prohibited;
**`retire`** is destructive and needs a type-the-name gate before it is offered (added 2026-08-30,
in both its forms — see [app.md](app.md)); **`add`** writes secrets and belonged with Phase 4
(added 2026-08-30, see Phase 4.5 below).

Provisioning is **not here**: it was solved in v1 by generating the artifact instead of running
it, and there is no intention of later "promoting" it to remote execution.

### Phase 4 — Environment variables — Done, 2026-08-30

An editor for `secrets/<instance>.env` with the schema derived from `services[].env` in
`apps.json`: which variables the app requires, which are missing, which are set. Write-only,
preserving 600 permissions. All of that, plus the part the description did not anticipate — a
saved change is not a live change, so the panel offers the redeploy that applies it.

The contract is `stack secrets <inst> {--json|--set}`, and the value travels on **stdin**: as an
argument it would be visible in `ps` on the server. Setting is limited to variables `apps.json`
declares; unsetting is not, so leftovers can be cleared. Reasoning in
[stack-integration.md](stack-integration.md), the UI in [app.md](app.md).

**Building it found a hole in Phase 3.** The atalaya account could write `stack` itself — the
program the dispatcher runs as an account in the docker group — because it is in the owner's group
and Ubuntu's default umask leaves group write on everything `git pull` writes. The allowlist was
bounding what could be asked for while the program answering could be replaced. Fixed in three
places, including a check inside the dispatcher that fails closed; see
[stack-integration.md](stack-integration.md).

### Phase 4.5 — Creating an instance — Done, 2026-08-30

`stack add` from the panel: the last thing that needed a terminal. Not a phase of its own when
this was written — it became one once the declaration stopped being a git-tracked file with two
owners, which is what made creating an instance an ordinary dispatcher entry rather than a fight
with the repository.

It is the widest entry in the allowlist and the only one carrying values that are not names, so
its dispatcher case parses its arguments instead of matching a fixed shape: each flag at most
once, each value against its own validator, anything unrecognised refused. What it may **not**
carry matters as much as what it may — `--catalogue` and `--secrets-dir` would point `stack` at
files of the caller's choosing.

Two entries for one command, as with `secrets`: `--dry-run` writes nothing and is a `read`, so the
panel shows what the server itself worked out — database, user, variables still to fill in —
before anyone commits to it. What is confirmed is what happens.

**It also fixed a real alert.** A newly declared instance was probed for its certificate before it
had one, so it alerted through the whole DNS-then-variables-then-deploy sequence. The probe list
now follows what is *deployed*, not what is declared.

### ~~Phase 5 — Deploying atalaya~~ — dropped, 2026-08-27

The plan was to add `atalaya` to `stack`'s catalogue and run it as one more instance, to avoid a
separate deployment mechanism for this one app. Dropped, for reasons that were already on the
page before this became a phase to schedule:

- **The identity models conflict.** atalaya is a loopback-bound process reading a header
  `tailscale serve` injects; `stack` reaches instances only through Traefik by domain. Putting
  atalaya behind `stack` reintroduces the container-cannot-reach-host-loopback problem
  `network_mode: host` exists to solve, and trades a tailnet-only identity for a public-domain
  one. See *Why not `stack`* in [app.md](app.md), which argued this before Phase 5 was revisited.
- **The mechanism it would replace is barely a mechanism.** Deploying atalaya is `git clone`,
  edit one file of two values, and three compose commands. That was true only after the install
  rework in Phase 2.6; the "separate deployment mechanism" this phase was written against — a
  scratch clone, a build, and a directory swap — no longer exists.
- **It would have atalaya deploy itself.** The audit row is written on completion, so the one
  action guaranteed to restart the process mid-run is the one that would never be recorded.

## Changes to the `stack` repo

Two, both small and of immediate value even if atalaya never gets built. **Both done**, see
*Both `stack` changes named in PLAN.md's "Changes to the `stack` repo"* in
[monitoring.md](monitoring.md) — names ended up English (`stack_backup_success`,
`stack_backup_last_success_timestamp_seconds`, `stack_deploy_info`,
`stack_deploy_timestamp_seconds`), not the Spanish ones written below when this was drafted, per
the later *English throughout* revision:

- **`scripts/backup.sh`** — besides writing `backups/last_status`, write a `.prom` file into
  node_exporter's *textfile collector* directory with a success gauge and a last-success
  timestamp. Roughly 10 lines, and in exchange backup status gains a year of history and an
  automatic alert of the "no successful backup for 26 hours" kind — which is what actually warns
  you when the cron job stopped firing.
- **`stack`** — on finishing a deployment, export the deployed version per instance the same way,
  as a metric with a `version` label, giving a deployment history. Nothing in atalaya queries it
  yet — see *Deployment history screen* in [monitoring.md](monitoring.md).

## Verification

- **Phase 0**: `promtool check config` and `promtool check rules`; confirm on Prometheus's web UI
  that the nodes show as `UP`; leave it 24 h and confirm the series is continuous. Break a backup
  on purpose and check the alert arrives.
- **Phase 1**: compare what the app shows against `./stack status` run by hand on each server —
  they must match instance for instance. Test with a server powered off: it must degrade, not
  break.
- **Security**: `ss -lntp` to confirm the process listens on `127.0.0.1` only. Try reaching it
  from another tailnet node bypassing the proxy and confirm it is refused. Try injecting a made-up
  instance name, or one with metacharacters, and confirm it is rejected before SSH is touched.
- **Phase 3**: a real `deploy` on `marsella-test` from the app, checking that `stack`'s automatic
  rollback still works and that the audit trail records it.

## Plan revisions

**2026-08-17 — Tailscale as a prerequisite, not a parallel task.** Collectors must bind to the
tailnet IP; without a tailnet there is nothing to bind them to. All four nodes joined that day.

**2026-08-18 — Provisioning stays outside atalaya.** The previous version left it as external
preparation, and turning it into remote execution from the application was considered. Discarded:
atalaya generates the artifact and verifies the result, but does not install. This removes the
need for remote `sudo` at the root, and lets server registration land in the read-only v1 instead
of waiting for Phase 3.

**2026-08-18 — Phase 0 cut to a single server.** The "instrument all three now because history
cannot be recovered" argument is dropped. `marsella-test` only; the other two via the generator,
which thereby tests itself.

**2026-08-18 — Alert delivery moves into atalaya, and channels stop being exclusive.** The
original plan had Alertmanager sending by Telegram. The split changes: Alertmanager forwards to
atalaya and atalaya notifies, because Alertmanager's configuration is file-only and the premise
is that this must be configurable from the web UI. Since delivery is then our own code, channels
coexist and are toggled from the UI rather than chosen once, routed by severity. Email transport
is left undecided.

**2026-08-18 — No bypass route; the watchdog runs through atalaya.** A static route in
`alertmanager.yml` bypassing the application was planned, and Telegram was picked for it. Dropped
on the objection that it made an unwanted channel load-bearing. Rethinking it showed the route
was redundant: routing the watchdog heartbeat *through* atalaya means its outage already stops
the pings and healthchecks.io reports it. One path, exercised every five minutes, instead of two
where the emergency one is never tested. Telegram leaves the design entirely.

**2026-08-18 — English throughout.** Repository language switched from Spanish to English, files
and CLI flags included. `stack` is to follow later. Two identifiers stay in Spanish because they
name things that already exist there. `stack` has since been translated too, so the label is
`stack.client` and the script `backup.sh`.
