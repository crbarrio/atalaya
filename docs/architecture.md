# Architecture

What atalaya is and how it is put together: the layers, the data sources, the constraints it is
built under and the reasoning behind the ones that look like limitations. This describes what is
built. How it got here, phase by phase, is in
[decisions/plan-phases-2026-08-17.md](decisions/plan-phases-2026-08-17.md).

## The problem it solves

Three servers (`madrid-prod`, `marsella-prod`, `marsella-test`) run the deployment engine from the
`stack` repo, and `homeserver` runs the household services. Before atalaya, every operation meant
SSH-ing into a machine and running `./stack` by hand: no combined view, no way to tell at a glance
which version each instance runs, whether last night's backup succeeded, or how much RAM and disk
headroom each machine has left, and no measured figure for what each client costs.

atalaya is a self-hosted web application on `homeserver` that unifies both halves: **commanding**
(running `stack` on any server, editing each instance's variables, links to the deployed domains)
and **watching** (CPU, RAM, disk, per-container usage, backup status, certificates, incidents),
in a single interface of its own, without jumping to external tools.

## Decisions in force

| Decision | Choice |
|---|---|
| Server access | SSH over Tailscale. No agent on the machines. |
| Metrics | Prometheus as an **invisible** engine. The UI is our own. |
| Presentation | Angular + Chart.js. No Grafana in the product. |
| Authentication | Tailscale Serve (`Tailscale-User-Login` header), development stand-in otherwise. |
| Commands | A fixed list of `stack` subcommands through a root-owned dispatcher on each server. |
| Provisioning | atalaya **generates the artifact and verifies the result**. It never installs. |
| Control node | `homeserver`, with its own SSH key. Not a workstation. |
| Prometheus targets | File-based discovery (`file_sd_configs`), regenerated by atalaya. |
| Alert delivery | Alertmanager groups and forwards to atalaya; **atalaya sends the notification**. |
| Alert channels | Several, coexisting. Enabled and routed per severity from atalaya's UI. |
| Monitoring the monitor | Watchdog heartbeat **through atalaya** to healthchecks.io. |
| Bypass route | None. See *Why there is no bypass route*. |
| Deployment of atalaya itself | A clone on `homeserver`, not a `stack` instance. See [decisions/deploy-outside-stack-2026-08-19.md](decisions/deploy-outside-stack-2026-08-19.md). |
| Stack | NestJS + Angular + Prisma + SQLite, laid out as in `compas`. See [app.md](app.md). |
| Language | English throughout, code and documentation alike. |

## Three layers, one of them ours

- **Collection and storage** — `node_exporter` + `cAdvisor` on each remote server (listening
  *only* on the Tailscale IP), `blackbox_exporter` and `Prometheus` on `homeserver`. Long
  retention (≈395 days). No interface; nobody ever opens it.
- **Rules and alerting** — Prometheus rules + Alertmanager, configured in YAML. Alertmanager
  delivers by webhook to atalaya, which stores and displays them.
- **Presentation and control** — atalaya. The only thing being developed.

atalaya's data sources:

1. **Prometheus HTTP API** (`/api/v1/query`, `/api/v1/query_range`, `/api/v1/alerts`) for every
   number and chart. atalaya **stores no metrics**; that is what keeps it small. Every PromQL
   string is a named entry in one catalogue in the backend; the frontend sends no PromQL.
2. **SSH** (`ssh2`) to run `stack`'s JSON contracts and, through the dispatcher, its actions.
   See [stack-integration.md](stack-integration.md).
3. **Alertmanager webhook** for the incident inbox and notification delivery.

SQLite holds only: the server registry, received incidents, notification channels (credentials
encrypted), disk alert preferences, the one global setting, the action audit trail, and a cache
of what `stack inventory` last reported. Nothing in it is a source of truth for the servers.

Two things `stack` does for atalaya's benefit: `backup.sh` writes its result as metrics into
node_exporter's textfile directory, and `stack` writes the deployed version per instance the same
way (`stack_deploy_info{app,version}`), which is what gives backup and deployment history without
an event log. Both in [stack-integration.md](stack-integration.md).

## Security — non-negotiable constraints

- The process listens on **`127.0.0.1` only**. Without this, Tailscale's identity header is
  forgeable by anyone on the tailnet. The guard refuses to trust the header otherwise: a
  misconfigured deployment loses access rather than silently losing authentication.
- `tailscale serve`, never `tailscale funnel`.
- **Never a free shell over SSH.** The backend composes `stack <subcommand> <instance>` from a
  closed list of subcommands, every value matched against a regex, forwarded as an argv and never
  re-split from a string. No interpolating user text into a command. `exec` and `engine` are not
  in the list and stay out.
- A dedicated SSH user per server, a key exclusive to atalaya, and exactly one `sudo` line: the
  account may run `/usr/local/sbin/atalaya-stack` as `ubuntu`, a root-owned dispatcher holding the
  list of `stack` subcommands it accepts. No wildcard, and the list is in a file the account cannot
  write. Nor can it write the program the dispatcher runs — the dispatcher checks that on every
  call and fails closed. Details and what it honestly costs in
  [stack-integration.md](stack-integration.md).
- **atalaya does not provision by itself.** It generates the installation artifact and checks the
  result, but a person supplies the `sudo` that installs it, once. This is not a limitation to be
  overcome later: it is what stops the panel from becoming a machine capable of installing
  software as root across the whole fleet. Running a fixed list of `stack` subcommands on an
  already-provisioned machine is a different thing, and is what the dispatcher bounds.
- The artifact is **downloaded and read before being run**. No `curl … | sudo bash`: the
  shortcut normalises running code nobody has looked at as root, and turns any flaw in atalaya
  into direct access to all three servers.
- Secrets are **write-only**: variables can be written and rotated, an existing value is never
  displayed. What *is* shown is *which variables are missing*, derived from the catalogue. A value
  travels from the request body to the SSH command's stdin and nowhere else.
- Every action with an effect is recorded in the audit table, with names and never values.

### Verifying the constraints

- `ss -lntp` on `homeserver` confirms the process listens on `127.0.0.1` only. Reaching it from
  another tailnet node bypassing the proxy must be refused.
- Injecting a made-up instance name, or one with metacharacters, must be rejected before SSH is
  touched. `setup-server.sh --check` asserts the dispatcher's refusals on the server itself.
- On each managed server, `sudo -n id` as `atalaya` must ask for a password; the same key over the
  public hostname must be refused. Both recorded in [infrastructure.md](infrastructure.md).
- Prometheus: `promtool check config` before touching a running instance; runbook in
  [monitoring.md](monitoring.md).

## The installation artifact

A single script, `infra/fleet/server-setup/setup-server.sh`, versioned in git: idempotent,
parameterised by arguments (host, tailnet IP, labels, ports) and readable in one sitting. atalaya
personalises it at registration by rewriting its own `--- Defaults ---` block, so running it needs
no flags. It installs the collectors, the `atalaya` account, the dispatcher and its sudo rule, and
verifies all of it; `--check` re-verifies and `--uninstall` removes the privilege with the rest.

**Bash, not Ansible.** Not a matter of taste: Ansible pushes from a control node towards the
machines, and the chosen model is the opposite — a self-contained artifact handed to the user to
run *on* the new machine. A playbook cannot be "downloaded and run there"; a script can.

## Server registration

Registration modifies no remote server: it only generates text and makes HTTP requests.

1. The server is registered by its tailnet name; the IP is resolved over MagicDNS and rejected if
   outside the CGNAT range, so a name that happens to resolve on the LAN cannot be registered
   pointing off the tailnet.
2. atalaya **generates the artifact already personalised** — that IP, its ports, the SSH key — to
   download.
3. A person runs it on the new machine, with `sudo`, having read it.
4. atalaya **verifies**: does `node_exporter` answer? Does cAdvisor? Does Prometheus see the
   target as `UP`? Three traffic lights, in that order, because the first two answer the moment
   the artifact finishes and the third proves the whole chain including the regenerated targets.

To close registration without editing files by hand, **Prometheus reads its targets through
file-based discovery** from JSON files atalaya regenerates from its database (`node`, `cadvisor`,
and `domains` for the certificate probes). Prometheus re-reads them on its own. Same pattern
`stack` already uses: the database rules, the configuration is derived.

## Alerting

Two separate things that are easy to conflate: **notifying** is pushing something at you when
you are not looking; **the inbox** is a place to review what happened. atalaya provides both,
and they are not alternatives.

### Where the configuration lives

Alertmanager is configured by a YAML file and has **no API for changing its configuration**.
Since "configurable from atalaya's web UI" is a premise, that constraint decides the design.

**Alertmanager forwards everything to atalaya over a webhook, and atalaya sends the
notification.** Recipients, channels, per-severity routing and per-disk mutes are rows in SQLite,
edited through the UI. No file generation, no reload, and no template bug that silently kills
alerting.

The alternative — atalaya generating `alertmanager.yml` and reloading — was rejected. It makes
the UI a disguised YAML editor: the form has to map onto Alertmanager's nested routing tree with
inheritance between levels, so atalaya would inherit Alertmanager's configuration model as its
own interface model. And a bad generated file breaks alerting silently, which is discovered on
the day the alert was needed.

What Alertmanager keeps is the hard part, which we do not want to reimplement: grouping,
deduplication, inhibition (do not report ten downed services when the truth is one downed
server) and silencing. **Silences do have a REST API**, so "silence this" from atalaya's UI is an
HTTP call, not a generated file. Configuration in our database, silences against their API, and
`alertmanager.yml` stays a short file that is versioned and rarely touched.

### Channels are not exclusive

Because delivery is atalaya's code rather than Alertmanager routing, channels are a table —
type, credentials, enabled, which severities it takes — and adding one is writing an adapter.
Email and Telegram coexist; each is switched on and configured from the UI, and verified against
the real service before the row is written.

They are complementary rather than interchangeable, by urgency. "Backup failed last night" or
"this disk fills in 4 days" are email: read calmly, with context, kept in the inbox.
"marsella-prod is not responding" is a push to the phone. That is routing by severity.

### Watching the watchman

Absence of alerts is ambiguous: everything may be fine, or Prometheus may have stopped three
days ago. From the inside those two states are identical, and no system reliably detects its own
death.

A `Watchdog` alert with `expr: vector(1)` is therefore permanently firing, and Alertmanager
forwards it as a steady heartbeat. **The heartbeat goes through atalaya**, which pings
**healthchecks.io** — an external service that does nothing while pings arrive and notifies when
they *stop*. The URL is the one value on the Settings screen.

Routing it through atalaya rather than around it is the deliberate choice. The heartbeat then
crosses the entire chain — Prometheus evaluating, Alertmanager routing, atalaya's notifier, the
home network, the internet link — so a break anywhere is noticed, including the two cases nothing
else covers: a power cut at home, and atalaya itself being down.

The watchman must be external. One running on the same machine watches nothing.

### Why there is no bypass route

The obvious objection to routing everything through atalaya is that its own outage would leave us
blind. The usual answer is a static route in `alertmanager.yml` that bypasses the application.
Rejected, for two reasons.

First, it is **redundant**. The failure it covers — atalaya down, notifications not going out —
is already detected by the watchdog, precisely because the heartbeat runs through atalaya. When
atalaya dies the pings stop and healthchecks.io says so, from outside.

Second, **an emergency path that is never exercised does not work.** A bypass used once a year is
where the token has expired, the address changed, or the provider altered its API — and nobody
noticed, because nothing ever travelled that way. The watchdog path is exercised every five
minutes and is therefore continuously proven.

The cost, stated plainly: while atalaya is down we get the fact that the system is broken, not
the content of the alerts. Alertmanager **retries the webhook**, so alerts still firing are
delivered once atalaya returns — a delay, not a loss; what can be missed is something that broke
and healed during the outage. And on being told the monitoring is down, the next action is to go
and look anyway, where the content is waiting.

### Alert fatigue

One downed server can generate dozens of notifications if grouping is left at defaults. By the
third day they stop being read and the system stops being worth anything. Grouping keys, wait
windows and repeat intervals are decided deliberately in `alertmanager.yml`, not inherited; the
notifier fires on the two edges only (first seen, firing → resolved), never on Alertmanager's own
repeats.
